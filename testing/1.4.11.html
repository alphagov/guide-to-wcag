How to test for 1.4.11 Non-text Contrast

WCAG says:

The visual presentation of the following have a contrast ratio of at least 3:1 against adjacent color(s):

  • User Interface Components: Visual information required to identify user interface components and states, except for inactive components or where the appearance of the component is determined by the user agent and not modified by the author;

  • Graphical Objects: Parts of graphics required to understand the content, except when a particular presentation of graphics is essential to the information being conveyed.

When this is applicable

If there are UI components and meaningful graphics.

Check colour contrast of graphics and UI components

“The aspects that define a control need reasonable contrast” – Alastair Campbell

Use the same tools as for 1.4.3 Contrast (Minimum).

Identify graphics that don’t have a visual label (text explaining the meaning or current state) and identify the parts of UI components that distinguish them as that component - for example, a circle outline for a radio button, or a solid-colour form field with a different colour from the rest of the page.

And identify other states of UI components (checkboxes, radio buttons, tabs, etc) and activate them one by one.

Check:

  • contrast of graphics against adjacent colours (often outside background colour, but can also be inside background colour or a border colour, doesn’t need to be all sides, can be just one side, like a bottom border)
  • contrast of the focus on UI components against adjacent colours
  • contrast of those bits that are required to identify the component/state to adjacent colours
  • when encountering mixed colours in graphics, that if the parts with low contrast were removed, the graphics could still be understood

W3C has a summary of these testing principles.

W3C’s ‘Understanding 1.4.11 Non-Text Contrast’ says:
“if a graphic is needed to understand the content or functionality of the webpage then it should be perceivable by people with low vision or other impairments without the need for contrast-enhancing assistive technology.”
However, this might not apply to accessibility overlays. Pages using this type of overlay can potentially result in an acceptable conforming alternate version if the method used is accessible itself, but ideally the page should be compliant without relying on an overlay.

Exceptions

  • inactive elements
  • default browser styles

Best practice

All parts of graphics (both meaningful and decorative) should ideally have sufficient contrast.

Mobile app testing

Do a visual check for likely contrast issues. If unsure whether something passes, take a screenshot and test it on a desktop.

On Android, contrast issues might also be picked up by the Android accessibility scanner.
