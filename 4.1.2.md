# 4.1.2 Name, Role, Value

## [WCAG says](https://www.w3.org/TR/WCAG22/#name-role-value):

> For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies.

## When this is applicable

When there are interactive elements.

## Check accessible name

Check:

* all interactive components (such as links, form elements and tabs) have an [accessible name](accessible-names)
* all frames and iframes have a `title` - in the [Web Developer extension](https://chrispederick.com/work/web-developer/), go to 'Information \> Display title attributes'

## Check semantics (role, value)

It should be clear to assistive technology users what an interactive component is doing.

Check whether interactive components use their [native semantic elements](semantics-and-specs#semantics) - these elements will usually be accessible. Divs and spans are never natively semantic for interactive elements. Having HTML knowledge will help you check this.

If interactive components do not use their native semantic elements, check:

* semantics have been added using ARIA
* ARIA is used correctly (according to the [spec](semantics-and-specs#specifications))
* ARIA has the appropriate effect on the element's role, value or both

When interacting with a component, check any values are changed appropriately. For example in an accordion, either the text toggles "show/hide", or the code changes the value of `aria-expanded`. Otherwise, check if context or explanatory text make it clear what happens.

You can use:

* a screen reader (ideally NVDA)
* [ARIA bookmarklet](https://pauljadam.com/bookmarklets/aria.html)
* [Visual ARIA bookmarklet](http://whatsock.com/training/matrices/visual-aria.htm)
* [WAI-ARIA usage bookmarklet](https://thepaciellogroup.github.io/WAI-ARIA-Usage/WAI-ARIA_usage.html)
* the code inspector and refer to [ARIA spec](https://www.w3.org/TR/wai-aria-1.1/) and [HTML in ARIA](https://www.w3.org/TR/html-aria/)
* some testing tools will tell if something is wrong with ARIA (like [axe](https://www.deque.com/axe/browser-extensions/))
* [WAVE](https://wave.webaim.org/extension/) visually shows some of ARIA

## Check dynamically hidden things

If anything is hidden visually, it should also be hidden programmatically.

For example:

* if error messages for form inputs are visually hidden but screen reader users can still read them and/or keyboard-only users can still tab to them, this would be a fail
* content that is hidden because it's in a different tab (or accordion) section and is shown later should also be hidden from assistive technology until it's revealed

Check this for both screen readers and keyboard-only. Alternatively, check the code has something like `display: none`, `aria-hidden` or `hidden`.

## Other ways to check

You can also check which semantics elements have by:

* checking the accessibility tree in the browser inspector
* searching for `aria` and `role` in the code - either search using the dev tools or use the [View Rendered Source extension](https://chrome.google.com/webstore/detail/view-rendered-source/ejgngohbdedoabanmclafpkoogegdpob?hl=en) (do not just use 'view source')
* checking if links have a valid `href` (not using a target of `#` or `javascript:`) - if they do not, it's a sign they are used as buttons or other interactive elements and not links and should have respective semantics (use [Web Developer extension](https://chrispederick.com/work/web-developer/) to list all `href`s of links by going to 'Information \> View Link Information')

## Best practice

It's good to produce valid HTML and ARIA, but not always necessary to pass WCAG (as long as it doesn't break anything else).

It's best to use native elements although it's possible to use ARIA to make something semantic.

If there are typos in the code (for example, `aria-hidden="treu"` or `aria-hiden="true"`) this may or may not be a fail depending on the context and whether that typo leads to names, roles or values not being programmatically determinable.

### Examples

```
<label for="col">Favourite colour</label>
<input type="text" id="col" aria-lable="Favourite colour" />
```

This would pass because the `aria-label` (with `aria-lable` misspelled) is not necessary here.

```
<label>Favourite colour</label>
<input type="text" aria-lable="Favourite colour" />
```

This would fail because there is nothing else labelling the input.

## Mobile app testing

For each interactive component, use a screen reader to check that it has an accessible name, is detected as the correct role and communicates its status correctly (if applicable).
