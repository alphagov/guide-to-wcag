# 2.4.11 Focus Not Obscured (Minimum)

## [WCAG says](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum):

> When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content.

## When this is applicable

When there are interactive elements (links, form elements or other interactive objects).  

## Identify overlapping components  

Identify parts of the page that might have overlapping interactive components, for example:

* sticky content which remains on screen when scrolling, such as a page header, sidebar menu or feedback widget
* expanding content, such as menus
* modal windows, such as a cookie consent pop-up, sign in prompt or warning pop-up  

You might need to:  

* activate page functionality, like a sign in window
* zoom the browser to 200% or 400% - this might trigger a 'mobile version' of a menu, or other dynamic content
* generate error messages
* view the site in an incognito window
* clear cookies

## Check visibility of components that are overlapped  

You may need to reload and reset the page before some checks. For example, clear any forms, remove error messages, and reset zoom.  

Tab through the page and review every interactive component that receives keyboard focus. When each component receives focus, check that the component (excluding its focus indicator) is not completely hidden by anything else on the page.

Then, one by one, open or trigger anything you’ve identified which could further overlap parts of the page and repeat the check. You might also need to test combinations of overlapping content, for example, opening a menu and a search bar at the same time.

There are some specific scenarios to consider:  

* If a component is obscured by content that a user has triggered, but the component can be made visible again without moving keyboard focus (such as by pressing the Escape key, or using the keyboard to scroll the content and reveal the item with focus), then it passes this criterion.
* If any components can be moved by the user, then only their original position on page load needs to be tested.
* If a component is completely hidden but the focus indicator is visible, it still fails this criterion.
* If a component is hidden when tabbing either backwards or forwards, it fails this criterion, even if the component is visible in one direction.
* If both the component and its focus indicator are invisible when the component receives focus, but the hiding is not due to another on-screen component, it fails [2.4.7 Focus Visible](2.4.7) instead.
* If a component is covered by a semi-transparent overlay but still partially visible, then it passes this criterion but the focus indicator might fail [1.4.11 Non-text Contrast](1.4.11).

## Best practice

* When focused, the entire component should be visible in order to meet level AAA; see [W3C's 'Understanding 2.4.12 Focus Not Obscured (Enhanced) (Level AAA)](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-enhanced)'.
* Keyboard focus should always be limited to the currently active layer of content, for example a modal window.
* All interactive components must have a visible focus indicator; this is covered under [2.4.7 Focus Visible](2.4.7).

## Mobile app testing

Use an external keyboard.
